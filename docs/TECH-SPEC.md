# Danang Guide — техническое описание системы

Документ для передачи подрядчикам и оценки стоимости работ.
Составлен по факту кода в репозитории, дата среза — 5 августа 2026 г.

---

## 1. Что это за продукт

Мобильный путеводитель по Дананту (Вьетнам) для русскоязычных туристов: куда сходить, как добраться, что происходит рядом. Места отбирает владелец гида вручную, лучшие помечаются знаком «Проверено гидом».

Система из трёх работающих продуктов на общем backend:

| Компонент | Что это | Кто пользуется |
|---|---|---|
| **Мобильное приложение** | Android + iOS, React Native / Expo | туристы |
| **Веб-клиент** | зеркало приложения в браузере | туристы без установки |
| **CMS владельца** | закрытая панель управления контентом | владелец гида |
| **Backend API** | Express + PostgreSQL на Railway | обслуживает всех |

Продукт работает: приложение собрано и опубликовано (Android `versionCode 23`, версия 1.0.17), backend развёрнут на Railway, контентом управляют через CMS.

## 4. Функциональность

### Мобильное приложение
Пять нижних вкладок: Главная, Поиск, Карта, Избранное, Помощь.

- **Главная** — баннер-шапка, популярные места, сетка категорий с собственными иконками, карусель подборок, блок советов
- **Категории** (15 шт.) — список мест, быстрые фильтры (завтраки, веган, с животными, для детей), поиск, pull-to-refresh
- **Карточка места** — галерея с полноэкранным просмотром, описание, адрес, телефон, сайт, часы, средний чек, теги, знак «Проверено гидом», шеринг, избранное
- **Маршрут до места** — 4 режима (пешком, скутер, велосипед, такси), полноэкранная карта, полилиния, пошаговые инструкции на русском, сводка «X км · ~Y мин», передача во внешний навигатор
- **Карта** — геолокация, кластеризация точек, зум/локация/компас, слой пробок
- **Городские маршруты** — 3 готовых прогулки (сейчас захардкожены в коде, не из CMS)
- **Доска объявлений** — просмотр и поиск по секциям, подача объявления с фото (до 6), «мои объявления», жалоба на объявление, скрытие автора
- **Профиль** — вход через Google / Apple / Telegram, push-уведомления об акциях, удаление профиля
- **Помощь** — каналы связи и экстренные контакты, редактируемые из CMS
- Онбординг при первом запуске, баннер «Нет соединения — показаны сохранённые данные»

### Веб-клиент
Повторяет мобильное приложение: главная, каталог по категориям с фильтрами, карточка места, поиск, избранное, карта, «Рядом» (радиус 2/5/10/25 км), программы, помощь, доска объявлений, авторизация. Плюс «скрытая тема» — 10 тапов по логотипу подгружают альтернативное оформление.

### CMS владельца
Вход по паролю на `/owner-login`, семь вкладок:

| Вкладка | Возможности |
|---|---|
| **Карточки** | CRUD мест, ~30 полей, постановка точки на карте мышью или поиском адреса, загрузка изображений со сжатием на клиенте, статусы draft / published / hidden |
| **Акции** | привязка к заведению, даты, статусы, **ручная рассылка push** со статистикой доставки |
| **Модерация** | пользовательские объявления по корзинам, работа с жалобами (5 причин, 3 действия), блокировка авторов |
| **Баннеры** | баннеры главной, порядок показа |
| **Советы** | заголовок, текст, ссылка, активность |
| **Контакты** | каналы связи и экстренные телефоны |
| **Клики** | аналитика: топ страниц, кликов, категорий, мест; сброс статистики |

## 6. Данные

### Два режима хранения
Переключение автоматическое: **PostgreSQL**, если задан `DATABASE_URL`, иначе — **плоские JSON-файлы** в `storage/`. В production при недоступной БД процесс намеренно падает (`exit 1`), чтобы не писать на эфемерный диск.

Файловый режим — полноценный дубль всей логики хранения: каждая операция реализована дважды. Это удваивает объём кода и требует двойного тестирования.

### PostgreSQL — 18 таблиц
`categories`, `places`, `place_images`, `media_files`, `users`, `user_favorites`, `content_reports`, `hidden_authors`, `blocked_authors`, `push_tokens`, `promotions`, `tips`, `collections`, `collection_items`, `home_content`, `support_content`, `app_settings`, `analytics_events`.

Миграций как механизма **нет**: схема эволюционирует идемпотентными `create table if not exists` + `alter table ... add column if not exists` прямо в коде, выполняются на каждом старте. Откат невозможен, история изменений не зафиксирована.

### Карточка места — ~50 полей
Категория, slug, название, описание, адрес, район, телефон, сайт, часы, средний чек, ценовая метка, кухня, тип, услуги, теги, флаги (завтраки / веган / питомцы / детские программы / бассейн / спа), TOP, знак качества с текстом, звёзды отеля, статус, порядок, координаты, обложка и галерея, автор, заметка модерации.

### Изображения
Загружаются **base64 внутри JSON** (не multipart), лимит тела 25 МБ, изображение до 8 МБ, видео до 20 МБ. Кладутся на локальный диск контейнера в `UPLOADS_DIR`. **Без примонтированного тома фото исчезают при каждом редеплое**, а записи в `media_files` остаются. S3/CDN не используется, серверной оптимизации изображений нет.

## 8. Отказоустойчивость

Продумана сознательно, это сильная часть проекта:

- **Контент — три уровня**: сеть → кэш `AsyncStorage` → встроенный демо-контент. Источник честно показывается пользователю красным баннером, сбой backend не выдаётся за реальные данные.
- **Маршруты — три уровня**: Google Routes API → legacy Directions API → прямая линия по haversine с оценкой времени. Прямая линия помечается «(по прямой)». Для скутера и велосипеда — авто-переключение на автомобильный режим (у Google нет велоданных по Вьетнаму).
- **Веб** кэширует контент в `localStorage` и фоново синхронизирует (60 с публично, 120 с в CMS).
- **Избранное** работает без входа, при авторизации сливается с серверным списком.
- Все внешние вызовы обёрнуты в `try/catch` и не блокируют интерфейс.

## 11. Технический долг и риски

Перечислено то, что подрядчик увидит в первую неделю и что влияет на смету.

**Архитектура**
1. `server/src/db.js` — 3 376 строк, `index.js` — 2 241 строка. Ни роутеров, ни сервисного слоя, ни DI. Вся логика хранения написана дважды (Postgres и файлы).
2. `mobile/App.tsx` — 4 697 строк, ~85 функций верхнего уровня, включая все SVG-иконки и полный `StyleSheet`. Все экраны в одном файле.
3. Дублирующие маршруты API: `/api/owner/places` и `/api/owner/listings` — два CRUD над одной сущностью.

**Производительность**
4. `/api/listings`, `/api/search`, `/api/listings/:slug` читают **весь** контент-стор из БД и фильтруют в JavaScript. Пагинации нет ни на одном публичном эндпоинте, кэша нет.
5. Push-рассылка идёт синхронно внутри HTTP-запроса — до 100 последовательных вызовов Expo API держат соединение CMS открытым. Очереди нет.

**Безопасность**
6. `helmet` отсутствует — нет CSP, HSTS, X-Frame-Options, nosniff.
7. CSRF-токенов нет, при этом CMS работает на cookie, а в native-режиме `SameSite` принудительно ослаблен до `None`.
8. Rate limit только на одном маршруте (вход владельца), in-memory — не переживает рестарт и не работает на нескольких инстансах.
9. Самописные реализации подписи токенов, верификации JWT по JWKS, парсинга cookie и чтения `.env` вместо проверенных библиотек. Работает, но это неаудированный код в самом чувствительном месте.
10. Схемной валидации входных данных нет — ручные `String(...).trim().slice(...)`.

**Эксплуатация**
11. Загруженные фото хранятся на диске контейнера — без тома теряются при редеплое.
12. Миграции без версионирования, откат невозможен.
13. Логирование — только `console.log`, без уровней, request-id и метрик. Нет graceful shutdown, пул Postgres при остановке не закрывается.
14. Expo Updates (OTA) отключён — любое обновление требует пересборки и публикации в сторах.

**Прочее**
15. Захардкожено в коде: тексты 4 юридических страниц с датой обновления, email поддержки, дефолтные контакты, dev-пароль, 3 городских маршрута, экран «Программы».
16. Дизайн-слой `mobile/src/design/` (тёмная тема, шрифты Prata / Onest / Manrope, собственные компоненты) написан, но к экранам ещё не подключён — продакшн-интерфейс пока светлый, со старыми стилями.
17. Корень репозитория замусорен ~20 отчётами о правках, в `docs/` ещё ~35 файлов. Онбординг-документации для подрядчика среди них практически нет.
18. Версия в `mobile/package.json` (1.0.8) расходится с `app.config.js` (1.0.17).

## 13. Возможные направления работ

Если задача — развитие, наиболее вероятный объём:

1. **Рефакторинг мобильного приложения**: разбор `App.tsx` на экраны, внедрение навигационной библиотеки, подключение готового дизайн-слоя
2. **Рефакторинг backend**: роутеры и сервисный слой, TypeScript, схемная валидация, версионируемые миграции, пагинация, кэш
3. **Безопасность**: helmet, CSRF, rate limiting на публичных эндпоинтах, замена самописной криптографии на проверенные библиотеки
4. **Инфраструктура**: вынос загрузок в S3/CDN с ресайзом, очередь для push, структурное логирование, мониторинг и крэш-репортинг
5. **Тестирование**: покрытие API-контрактов и ключевых пользовательских сценариев
6. **Продукт**: перенос захардкоженного контента (городские маршруты, программы) в CMS, OTA-обновления, локализация
